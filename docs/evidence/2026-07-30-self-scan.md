# Aker Build scanned against itself — 2026-07-30

Aker Build's dogfood workflow runs the tool on its own repository. This document
records what that scan actually produced, including the part that does not
flatter the tool. It is the "run it on real code and publish the result" artifact
from `docs/superpowers/specs/2026-07-30-uniqueness-repositioning-design.md`.

Reproduce:

```bash
pnpm dlx tsx packages/cli/src/bin.ts check . --out .aker-build
```

Figures below were re-verified at commit `f1c3a44` (workspace manifest detection),
which changed what `detectStack` reads. Every number reproduced unchanged: the fix
now scans all 46 tracked `package.json` files instead of the root alone, and finds
no web framework or ORM in any of them — so the empty coverage below is a measured
result, not an artifact of reading only a dependency-free root manifest.

## The honest reading: 76% of findings are self-inflicted

| Location | Findings | Share |
|---|---|---|
| Test fixtures | 26 | 76% |
| Product source | 5 | 15% |
| Detector source | 3 | 9% |

Aker Build is a static analyzer for multi-tenant SaaS. Its own test suite is
**full of deliberately-vulnerable fixtures** — unguarded admin routes, queries
without tenant filters — because that is what a detector's tests must contain. So
the tool flags its own fixtures, correctly, as vulnerable code.

The sharpest example: `packages/scanner/src/detect/data-access.ts:16` is flagged
as "DB query without a tenant filter." Line 16 is the `TENANT_TOKEN` regex — the
pattern that *defines* what a tenant filter looks like. The detector reads its own
definition as a violation.

**None of these are bugs in the detectors.** Each finding is locally correct: the
flagged line really does look like an unguarded route or an unscoped query. The
problem is that "locally correct" is not the same as "useful," and a tool that
reports 34 findings on a repository with no database and no web server is
producing noise a user has to filter.

## What this means for adoption

Any repository containing security test fixtures — most security-adjacent
codebases, and every codebase that tests its own authorization — will see the same
pattern. Three consequences worth stating plainly:

1. **Path scoping is not optional.** `aker-build.config.json` supports path scope;
   this scan deliberately ran without it, to show the unscoped baseline. A real
   adoption should exclude `**/tests/**` and fixture directories, and the
   quickstart should say so rather than leaving users to discover it via 26 false
   alarms.
2. **The `suspected`/`confirmed` split does not rescue this.** The tier separates
   *provable* from *heuristic*, not *interesting* from *noise*. A fixture's
   unguarded route is `confirmed` and correct — and still not worth a user's
   attention.
3. **This is the strongest argument against P6 (blocking checks).** Enforcement on
   this output would block merges on test fixtures. The roadmap already gates P6
   on measured precision; this scan shows measured precision against a benchmark
   is necessary but not sufficient — real-repo *relevance* is a separate axis and
   is currently unmeasured.

## Coverage reported honestly

The scan reports `covered: []`, `uncovered: []`, which is correct: Aker Build
uses no web framework and no ORM. It is a CLI that reads other repositories'
source. So "no findings in covered frameworks" is vacuously true here, and the
coverage field says so rather than implying the stack was understood.

This also means **this scan does not exercise the flagship detector against a real
consumer.** A genuine multi-tenant TypeScript application remains the missing
evidence; see the open question in the design document about which repositories to
use and how to establish ground truth on them.

## What was found in product source

The 5 product-source findings are the ones worth a maintainer's time — they are
recorded here rather than fixed, because fixing them is out of this document's
scope and each needs its own judgment:

- TG-G0 (source truth), TG-G2 (contract), TG-G3 (migration safety), TG-G8
  (dependency), TG-G9 (release readiness) — one finding each, all advisory.
- The TG-G4 and TG-G5 findings in product source are in the detector and gate
  modules themselves, i.e. pattern definitions being read as the thing they
  define.

## Limitations of this document

- One repository, and an unrepresentative one (a CLI, not a SaaS app).
- No ground truth: nothing here establishes what the tool *missed*, only what it
  reported. The design document's open question on that is unresolved.
- Findings are counted, not individually adjudicated beyond the location
  categories above.
